Privacy Guide

CyberWatch is designed specifically around session event monitoring, not content surveillance. This page documents exactly what data CyberWatch captures, where it goes, and what it explicitly never touches.

What CyberWatch Monitors

CyberWatch listens to two Windows subsystems:

1. WTS (Windows Terminal Services) Session Notifications

These are operating system–level signals that Windows itself generates for session state changes. CyberWatch receives the same signals Windows uses for its own session management:

  • WTS_SESSION_LOCK — screen lock event
  • WTS_SESSION_UNLOCK — screen unlock event
  • WTS_SESSION_LOGON — user logon
  • WTS_SESSION_LOGOFF — user logoff

These events contain a session ID and timestamp only. They do not contain any user content, files, or activity data.

2. Windows Event Log

CyberWatch reads two specific Event IDs from the Windows System log at startup:

  • Event ID 1074 — initiated shutdown or restart (contains initiator process name and reason code)
  • Event ID 6008 — unexpected power-off detected on the previous boot

These are standard Windows audit events. CyberWatch reads only the timestamp and event description — no user data is involved.

What CyberWatch Does NOT Capture

The following are explicitly excluded from CyberWatch's design and implementation:

  • No keystroke logging. CyberWatch registers no keyboard hooks and captures no keyboard input.
  • No password capture. CyberWatch does not hook Windows credential providers or authentication APIs.
  • No clipboard access. CyberWatch does not read from or write to the Windows clipboard.
  • No screen capture or screenshots. CyberWatch makes no graphics API calls related to screen content.
  • No browser history or URL tracking. CyberWatch does not access browser storage, process memory, or network traffic.
  • No webcam or microphone access. CyberWatch registers no media capture devices.
  • No file system scanning. CyberWatch does not scan, read, or index user files.
  • No process enumeration. CyberWatch does not enumerate or inspect running processes.
  • No network traffic inspection. CyberWatch makes a single outbound connection — to your SMTP server — to deliver email alerts.
  • No cloud telemetry. CyberWatch does not send usage data, crash reports, or analytics to any server.

Where Data Is Stored

CyberWatch stores two types of data, both exclusively on your local machine:

SQLite Event Database

Located at %LOCALAPPDATA%\Programs\CyberWatch\data\cyberwatch.db. Contains a record of each detected security event: type, timestamp, and session ID. No personal content.

Application Log

Located at %LOCALAPPDATA%\Programs\CyberWatch\logs\cyberwatch.log. Contains rotating log entries of agent activity. SMTP credentials are never written to logs.

SMTP Credential Handling

CyberWatch requires your Gmail App Password to send alerts. This credential:

  • Is stored in a .env file in the installation directory.
  • Has Windows file permissions set to owner-only read/write (via icacls).
  • Is never written to log files in any form.
  • Is never transmitted to any server except Gmail's SMTP server (smtp.gmail.com:587) over an encrypted STARTTLS connection.
  • Is never sent to the developer or any third party.
Your App Password belongs to you. Never share it with anyone — including the developer of this software. If you believe your App Password has been compromised, revoke it immediately at myaccount.google.com/apppasswords and create a new one.

Limitations and Scope

CyberWatch was built for personal use on your own device. It is not a commercial product and carries no formal security certification or compliance guarantee. It is provided under the MIT License for personal use on your own machine.

If you are installing CyberWatch on a device you do not own, you are responsible for ensuring you have appropriate authorisation to run monitoring software on that device.
